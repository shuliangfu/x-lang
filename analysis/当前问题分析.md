## 0. 问题概述

**核心症状**：单文件 `check` 干净通过；目录 `check` 时部分文件的 parser 从文件中间开始解析（跳过前 4000+ 行），导致 num_funcs 远低于实际值，下游 typeck 报 T001 unresolved function call + XP003 pipeline failed。

```
单文件:  ./compiler/xlang check compiler/src/runtime_pipeline_abi.x       → num_funcs=363 ✓
目录:    ./compiler/xlang check compiler                                   → num_funcs=111 ✗ (同一文件)
```

**受影响文件**（单文件通过、目录失败的文件，共约 3 个）：

| 文件 | 单文件 num_funcs | 目录 num_funcs | 单文件 num_defined | 目录 num_defined | num_extern (相同) |
|------|-----------------|---------------|-------------------|-----------------|------------------|
| `src/runtime_pipeline_abi.x` | 363 | 111 | 271 | 19 | 92 |
| `src/runtime_driver_abi_thin.x` | 377 | 190 | 260 | ? | ? |
| `src/asm/runtime_thread_glue.x` | 通过 | 失败 | ? | ? | ? |

**num_extern 完全相同**（92=92），说明 extern 声明被正确解析，但 **defined 函数** 大量丢失（271→19）。这意味着 parser 在解析"带函数体的 function definition"时提前停止。

## 1. 已完成的修复（wave1223 — 不要重复）

### 1.1 L003 假报错已修复

**原根因**：`pipeline_parse_set_main_from_buf_c` 在 `src/runtime_pipeline_abi.x` 中是**空 stub**（`return 0`），通过链接顺序覆盖了 C authority 的强符号，导致目录模式下 pipeline 路径调用此空 stub，文件被静默跳过（num_funcs=0 → 92 L003/P001/CHK001）。

**修复**：wave1223 在 `src/runtime_pipeline_abi.x` 实现了完整的 `pipeline_parse_set_main_from_buf_c` 函数体（委托给 C authority `pipeline_parse_into_with_init_buf_scalars`）。

**结果**：92 个 L003 + 81 个 P001 + 83 个 CHK001 全部消除。但暴露了更深层的问题：parser 在目录模式下仍然不完整解析某些大文件。

### 1.2 当前代码状态

`src/runtime_pipeline_abi.x` 的 `pipeline_parse_set_main_from_buf_c`（wave1224）：
```rust
#[no_mangle]

  if (m == 0 as *u8) { return 0 - 2; }
  if (a == 0 as *u8) { return 0 - 2; }
  if (d == 0 as *u8) { return 0 - 2; }
  if (len <= 0) { return 0 - 2; }
  unsafe {

      return 0 - 2;
    }
    pipeline_module_set_main_func_index(m, main_idx);
    return 0;
  }
  return 0 - 2;
}
```

## 2. 当前核心问题：parser 从文件中间开始解析

### 2.1 关键证据（parse commit debug）

启用 `XLANG_DEBUG_PIPE=1 XLANG_DEBUG_PARSE_COMMIT=1` 查看 parser 的 block commit 日志：

**单文件模式**（正常）：
```
note: parse commit debug: byte=0 num_funcs=0 phase=pre_fill  block=2  name=parser_parse_into_init       (文件第 499 行)
note: parse commit debug: byte=0 num_funcs=0 phase=post_block block=2  name=parser_parse_into_init
note: parse commit debug: byte=0 num_funcs=0 phase=pre_fill  block=3  name=parser_get_module_num_imports (文件第 ~550 行)
note: parse commit debug: byte=0 num_funcs=0 phase=pre_fill  block=6  name=parser_get_module_import_path
note: parse commit debug: byte=0 num_funcs=0 phase=pre_fill  block=14 name=parser_copy_module_import_path64
...
→ 最终 num_funcs=363, num_defined=271
```

**目录模式**（异常）：
```
note: parse commit debug: byte=0 num_funcs=0 phase=post_block block=29 name=pipe_pctx_off_entry_dir_buf  (文件第 4268 行!)
note: parse commit debug: byte=0 num_funcs=0 phase=pre_fill  block=30 name=pipe_pctx_off_entry_dir_len
note: parse commit debug: byte=0 num_funcs=0 phase=pre_fill  block=31 name=pipe_pctx_off_num_lib_roots
note: parse commit debug: byte=0 num_funcs=0 phase=pre_fill  block=32 name=pipe_pctx_off_loaded_len
...
→ 最终 num_funcs=111, num_defined=19
```

### 2.2 矛盾点

1. **block 编号跳过前 28 个**：单文件从 `block=2` 开始，目录从 `block=29` 开始 → block pool 的索引没有被正确重置，或者 parser 真的跳过了前 28 个 block。
2. **byte=0 但函数名是文件后面的**：`byte=0` 说明 parser 认为它在文件开头，但解析出的函数名 `pipe_pctx_off_entry_dir_buf` 在文件第 4268 行。
3. **num_extern=92 完全相同**：extern 声明被正确解析，说明 parser 确实读到了文件内容，但在解析 defined 函数时提前停止。
4. **src_len=355182 完全相同**：读到的源文件是同一个，buffer 内容正确。

### 2.3 推断

parser 的 **lexer cursor** 或 **block pool next_index** 在目录模式下没有被正确重置到文件开头，导致 parser 从文件中间位置开始解析。

可能的原因：
- `parser_collect_imports_buf`（seed L8413）在收集 imports 时把 lexer cursor 推到文件末尾，`parser_copy_lex_from_import_into`（seed L8414）没有正确恢复 cursor 到文件开头。
- 但单文件模式也走同一路径 → 所以问题在于**某个跨文件未清理的全局/static state** 污染了 parser 状态。

## 5. 剩余未知点（grok 要解决的核心问题）

### 5.1 核心问题

**为什么目录模式下 parser 从 block 29（文件第 4268 行）开始解析，而不是 block 2（文件第 499 行）？**

### 5.2 最强假设：parser 全局/static state 跨文件泄漏

`parser_parse_into_buf`（seed L8369）内部虽然在入口重置了 sticky flag，但 parser 可能还有其他全局/static state 没有被重置：

1. **`g_parser_match_module_x`**（x_seed_bridge.from_x.c L171）：全局 static，指向当前 module。`pipeline_strict_parse_into_init` 通过 `pipeline_parser_set_match_module(module)` 设置。如果 parser 在解析过程中通过 `pipeline_parser_get_match_module()` 获取此指针，而前一个文件的解析修改了某些与 module 关联的全局 state...
2. **lexer 全局 state**：`parser_collect_imports_buf`（seed L8413）创建一个 `struct lexer_Lexer lex = lexer_init()` 然后传给 `parser_collect_imports_buf`。如果 `lexer_init()` 内部引用了某些全局/static state（如 token cache、keyword table cursor），这些可能在跨文件时泄漏。
3. **parser block pool next_index**：如果 block pool 的 next_index 是全局/static 而非 arena-local，前一个文件的 block 会占据前 28 个 slot，导致当前文件从 block 29 开始。
4. **`parser_sig_type_hard` 类的 sticky flag**：wave676 修了一个（seed L8384-8388），但可能还有其他类似的 sticky flag 未被发现。
5. **trait registry / generic bound scan**：虽然 `xlang_trait_reg_reset_c` 和 `xlang_generic_bound_stash_source_buf_c` 在入口被调用，但它们内部的全局 state（如 trait name table、return kind table）可能没有完全清理。

### 5.2 待排查的代码路径

1. **`parser_collect_imports_buf`**（seed L8413）：收集 imports 时 lexer 扫描整个文件，cursor 到达文件末尾。`parser_copy_lex_from_import_into`（seed L8414）复制 lexer 状态。检查这个复制是否正确恢复 cursor。
2. **`lexer_init()`**：检查是否完全初始化了所有 lexer 字段，还是依赖某些全局/static 默认值。
3. **parser 的所有全局/static 变量**：用 `grep -n "static.*g_parser\|static.*g_lexer\|static.*g_typeck" compiler/parser_gen.c compiler/lexer_gen.c compiler/seeds/*.c | head -50` 列出全部，逐一排查。
4. **`pipeline_parser_set_match_module` / `pipeline_parser_get_match_module`**：检查 parser 在解析过程中如何使用 match_module，是否有通过 match_module 访问前一个文件的数据。
5. **`pipeline_module_reset_parse_counters_c`**：检查它是否重置了所有 parse 计数器，还是漏了某些。

## 8. wave1225 已落地（sidecar release-before-free）

### 8.1 根因类：free 不 release 进程级 sidecar

| 路径 | 问题 | 修复 |
|------|------|------|
| 产品 mono `driver_run_compiler_parsed`（`seeds/rt_run_compiler_parsed.from_x.c`） | 多处 `free(arena/module)` 不 release；二次 parse 前 `memset` 不 release | `rt_cp_release_arena_module` + reparse 前 release |
| `xlang_collect_deps_transitive` / dep prerun map 临时 arena | `free(tmp_arena)` 不 release → 槽泄漏 + 地址复用 | `pipe_release_tmp_arena_module`（`.x` + seed） |
| `driver_parsed_work_cleanup`（thin + C seed） | 原只 free；产品 mono 路径**不调用** cleanup | 已补 release；**产品当前仍走 mono 体**，cleanup 非热路径 |
| `pipeline_dep_ctx_heap_destroy` | 只 `free(ctx)`，`g_xlang_depctx_sc`（**MAX=64**）永不归还 | `pipeline_dep_ctx_sidecar_release` 后 free |

### 8.2 验证证据（wave1225）

- `XLANG_DEBUG_SIDECAR=1`：可见 `arena release` / `depctx release`；文件间 `used` 回到 1/512。
- 小文件在 `parser.x` 失败后仍完整 parse（`/tmp/bigish.x` → num_funcs=11）。

### 8.3 wave1226 已落地（onefunc heap scratch 泄漏 → mid-file soft-skip）

**根因**：`parse_block_into` 对嵌套 block 做 `calloc(sizeof OneFuncResult)`，经 `ast_pool_onefunc_reset` **创建** 进程级 `g_onefunc_sc[]` 槽，但成功/失败路径均 **不** `ast_pool_onefunc_release` + `free`。嵌套 block 多的大文件（尤其 `parser.x`）把 `MAX_ONEFUNC_SIDECARS=1024` 灌满；下一文件 defined 函数 body parse 全 `set_onefunc_fail` → soft-skip，**num_extern 仍满、num_defined 暴跌**（366→113）。

**证据**：
| 探针 | wave1225 后 | wave1226 后 |
|------|-------------|-------------|
| `parser.x` → `runtime_pipeline_abi.x` num_funcs | 113 | **366** |
| `parser.x` → `typeck.x` | 271 | **464** |
| `parser.x` → `backend.x` | 200 | **406** |
| onefunc used 峰值 / CREATE FULL | 1024 / 1409 次 | **4 / 0** |
| 单文件 abi | 366 绿 | 366 绿 |

**修法（根源，非 symptom）**：
- `.x`：`parse_block_into` 仅负责 calloc → `parse_block_into_with_scratch` → **always** `ast_pool_onefunc_release` + `free`
- seed：`parser_parse_block_into` 同构 wrapper（`seeds/parser_gen.linux.x86_64.c` → `parser_gen.c` → `parser_x.o`）
- `ast_pool.c`：`XLANG_DEBUG_SIDECAR` 下 onefunc create/release/FULL 探针（env 门闩，可留）
