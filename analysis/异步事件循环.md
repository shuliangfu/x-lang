## 1. 背景与动机

### 1.1 历史痛点

在用 Zig 实现 JS 运行时 shujs 时，推进到高并发网络 + 事件循环 + 与引擎深度绑定阶段卡住：

- 需要单线程（或可控线程数）下的高并发 TCP/HTTP/WebSocket
- 需要稳定的异步 I/O 与事件调度
- 上游对 Evented / 网络支持不完整（例如 Zig #31723：`std.Io.Evented has no networking support` 至今仍为实验/未完成）
- 为补齐能力最终混入 C（如 TLS），违背「尽量纯净实现」的目标

这直接推动了 xlang 的诞生目标之一：**完善、高性能、高安全、高可读、低学习成本** 的系统语言，并在异步 I/O 上做到「能用、好用、可预期」。

### 1.2 当前仓库现状（简要）

| 模块 | 现状 | 说明 |
| --- | --- | --- |
| std/io | 部分可用 | core / driver / backend / sync / win32；**Linux io_uring 金标主路径已生产可用**；macOS 走 sync 回退（无独立 kqueue 后端）、Windows IOCP 仅探针级（同步 ReadFile/WriteFile）。三端 Evented 成熟度详见 [async-platform-matrix.md](async-platform-matrix.md) §1 |
| std/net | 较完善 | TCP/UDP、listen/connect/accept、batch accept/connect、stream batch I/O |
| std/async | 基础可用 | 协作调度 POC、CPS、Future/Poll、io_uring 路径、多 worker 预览；仍有 C glue |
| std/task | 基础 | TaskGroup / JoinSet / Context 取消 / Supervisor |
| 统一事件循环 | 未定型 | 缺统一 Reactor、完整取消/超时模型、与语言层 async/await 的稳定契约、跨平台一致行为 |

**结论**：零件已有，整机（统一、可组合、高性能的事件循环运行时）尚未定型。适合在自举完成后做一轮架构收敛与性能打磨。**注意**：平台后端的"已实现/探针/回退"状态以 [async-platform-matrix.md](async-platform-matrix.md) 为准，本文不再单独维护一份。

## 2. 目标与非目标

### 2.1 目标（Must / Should）

**高性能**

- 单核 I/O 密集场景接近或超过精心手写的 io_uring / kqueue 循环
- 调度开销目标：协作切换 ≤ 数 ns～十几 ns 量级（已有 bench 方向）
- 支持 batch / multishot / 注册缓冲等现代内核能力

**高安全（对齐 xlang 安全子集）**

- 默认路径无 silent UB
- 取消、超时、生命周期与 region/borrow 可静态或可审计
- 显式错误（Result / error set），不吞错误

**高可读 + 低学习成本**

- 用户代码尽量像「同步逻辑 + await」，而不是手写状态机
- 或提供清晰的手动 Poll/Future API（双轨：易用 + 可控）
- 少魔法：调度器、取消、线程模型可解释

**跨平台一致语义**

- Linux：io_uring 优先
- macOS：kqueue / GCD 类后端
- Windows：IOCP
- 同一套高层 API，后端可替换

**可组合**

- 与 std.net / std.fs / std.http / 未来信号、定时器统一挂在同一 Reactor 上
- 支持「纯事件循环」与「多 worker + 亲和」两种部署

### 2.2 非目标（短期）

- 不追求完整彩色 async 传染全语言（可先库级 + 有限语法糖）
- 不在自举完成前重写整套 std
- 不强制用户必须用绿色线程；允许显式选择 Threaded / Evented 风格（参考 Zig std.Io 思路，但补齐网络）
- 不把「像 Node 一样默认单线程事件循环」作为唯一模型

## 3. 业界对照（设计参考）

| 方案 | 模型 | 优点 | 缺点 | 对 xlang 的启示 |
| --- | --- | --- | --- | --- |
| libuv / Node | 单线程事件循环 + 线程池 | 成熟、生态大 | 回调/心智负担、与系统语言安全模型弱结合 | 可学 Reactor 结构，不学默认回调风格 |
| Tokio (Rust) | 多线程 work-stealing + mio/io_uring | 性能强、生态全 | 学习成本高、运行时重 | 任务调度与取消可参考，语法负担要降低 |
| Zig std.Io | Io 接口：Threaded / Evented | 可替换后端、显式 | Evented 网络仍不完整、实验性强 | 接口可替换很好；xlang 必须把网络做完整 |
| io_uring 原生 | 提交/完成队列 | 吞吐极高 | 平台绑定、API 陡 | Linux 主路径应直通，少一层无谓抽象 |
| Go runtime | M:N + netpoller | 开发体验好 | GC、调度不可控 | 体验可学，运行时重量不可学 |

**xlang 应走的路线**：显式 Io / Reactor 接口 + 协作任务（可选多 worker）+ 平台最优后端 + 安全默认值。

既避免 Zig 式「Evented 半成品」，也避免 Rust 式「运行时+类型系统双重税」。

## 4. 推荐架构

### 4.1 分层

```
┌─────────────────────────────────────────────┐
│  用户代码 / std.http / std.net 高层 API      │
│  (async fn / await 或 Future 组合)           │
├─────────────────────────────────────────────┤
│  std.task  (TaskGroup, 取消, JoinSet)       │
├─────────────────────────────────────────────┤
│  std.async (Executor / Scheduler / Future)  │
├─────────────────────────────────────────────┤
│  Reactor / EventLoop  (统一等待与唤醒)        │
├─────────────────────────────────────────────┤
│  std.io.driver  (submit / complete / batch) │
├─────────────────────────────────────────────┤
│  Backend: io_uring | kqueue | IOCP | poll   │
└─────────────────────────────────────────────┘
```

### 4.2 核心对象

**Reactor（事件循环内核）**

- 注册：fd / 定时器 / 自定义唤醒
- `poll(timeout)` → 一批就绪事件
- 与 std.io 的 completion 队列对接

**Executor / Scheduler**

- 已有：协作帧、CPS、MPSC ready ring、多 worker 预览
- 目标：稳定 API，去掉/收缩 C glue，纯 .x 或最小化 FFI

**Future / Task**

- `Poll::Pending | Ready(T)`
- 与取消 token、超时、Context 绑定
- 已有 `future_*` 与 `std.task` 可收敛为统一模型

**IoHandle**

- 对 fd/socket 的安全包装
- 所有权明确（对齐 xlang region / owned 语义）
- `read_async` / `write_async` / `accept_async` 返回 Future

### 4.3 两种运行模式（建议同时支持）

| 模式 | 适用 | 行为 |
| --- | --- | --- |
| Evented（默认推荐 I/O 密集） | 网络服务、代理、运行时 | 单线程或少量线程 + Reactor；任务协作调度 |
| Threaded | CPU 密集、简单脚本 | 阻塞 syscall + 线程池；同一套高层 API |

通过「Io 后端可替换」保持 API 稳定（学 Zig，但把网络补全）。

## 5. 关键设计决策

### 5.1 异步语法：库优先，语法渐进

**阶段 1（自举后立刻）**

- 稳定 Future + await 作为库函数 / 内置原语
- 用户可写手动状态机或用宏/编译器降糖

**阶段 2**

- 语言级 `async fn` / `await`（若已有关键字，补全语义）
- 编译器生成状态机或 CPS（你已有 CPS 路径可复用）

**原则**：可读优先，不强迫全程序 async 染色。

### 5.2 取消与超时必须一等公民

否则高并发服务无法用：

- Context / CancelToken（`std.task` 已有雏形）
- 所有阻塞点可响应取消
- 超时 = 取消 + 定时器事件
- 后端差异（Evented vs Threaded）要在文档中写清，避免「同一代码不同行为」的陷阱（Zig 社区已踩过）

### 5.3 内存与安全

- 任务帧：优先静态 / arena / 区域分配，避免热路径 malloc（与现有 no-malloc 调度方向一致）
- Future 的生命周期与 buffer 借用由 region/borrow 检查
- `unsafe` 仅出现在 backend 与极薄 FFI

### 5.4 与 net/http 的集成

自举后优先打通的端到端路径：

- `TcpListener::accept_async` → `Future<TcpStream>`
- `TcpStream::read_async` / `write_async`
- 多连接在同一 Reactor 上并发
- HTTP server 基于上述路径（可先 keep-alive + 有限并发）

这正好对标当年 shujs 卡住的场景，也是对外叙事的核心卖点。

## 6. 平台后端策略

> **三端后端成熟度、门禁、T\* 硬标准不在本文维护**，统一见 [async-platform-matrix.md](async-platform-matrix.md)。当前一句话：**只有 Linux io_uring 是金标主路径**，macOS 走 sync 回退（kqueue 未落地），Windows IOCP 仅探针。

本文只规定**后端接入 Reactor 的最小契约**（与平台无关的架构约束）：

| 契约方法 | 语义 | 用途 |
| --- | --- | --- |
| `submit` | 提交一批 I/O 请求（read/write/accept/connect/multishot） | 入队，不阻塞 |
| `complete` | 取回一批已完成 CQE（含 user_data + result + flags） | 驱动 Future 唤醒 |
| `wakeup` | 从外部线程/信号唤醒正在 `poll` 的 Reactor | 取消、定时器、跨线程 spawn |
| `cancel` | 请求中止一个 in-flight 操作 | 取消传播（详见 §5.2） |

**约束**：

- Backend 实现放在 `std/io/backend*` / `std/sys/*`（如 `linux_io_uring.x`、未来 `macos_kqueue.x`、`windows_iocp.x`）。
- Reactor 只依赖上述「可提交、可完成、可唤醒、可取消」四个方法，不感知平台细节。
- `cancel` 的语义差异（io_uring 部分 / kqueue ❌ / IOCP ❌，见矩阵 §2）必须在 backend 层吸收，不得泄漏到上层 Future。
- 每个新 backend 必须按矩阵 §2 的「平台矩阵硬标准」对齐 Threaded / Evented / multishot / cancel 四项，否则不进 `run-all.sh` 白名单。

## 7. 与现有代码的收敛建议

### 7.1 保留并强化

- std/io 的 submit/complete、batch、buffer 注册
- std/async 的协作调度与 Future/Poll
- std/net 的 batch accept/connect
- std/task 的结构化并发原语

### 7.2 需要收敛/清理（自举后）

- **统一入口**：`std.async.Runtime` 或 `std.io.EventLoop` 一个主类型，避免多套「pump/drain」并存
- **去 C glue**：`scheduler_glue.c` 逐步迁到 `.x` + 最小 sys FFI（符合全仓库去 C 终局）
- **网络 Future 化**：accept/connect/read/write 全部可走 async 路径，且与 Reactor 同一套完成队列
- **文档与门禁**：每个后端一份行为矩阵（取消、超时、错误码）

### 7.3 建议的模块边界

```
std/async/
  runtime.x      // 总入口：run / block_on / spawn
  executor.x     // 调度
  future.x       // Future/Poll
  reactor.x      // 事件循环（或放到 std/io）

std/io/
  driver.x       // 提交完成
  backend_*      // 平台

std/net/
  * 全部通过 Io/Reactor 挂接，不自己造第二套循环
```

## 8. 分阶段实现路线（自举完成之后）

### Phase 0 — 冻结与审计（1–2 周）

- 梳理现有 async/io/net 调用图
- 列出重复 API、C 依赖、未覆盖的取消/超时路径
- 定「对外稳定 API」白名单

### Phase 1 — 统一 Reactor + Linux 主路径

- 单一 poll 循环驱动 io_uring CQ
- TcpListener/TcpStream async 端到端
- 单线程高并发 echo / HTTP 基准

### Phase 2 — 任务系统与取消

- 稳定 spawn / JoinSet / Context
- 超时与取消在 net 路径上正确传播
- 多协程 + 有限 in-flight 槽位压测

### Phase 3 — 多 worker 与亲和

- 已有 MPSC / workers 预览产品化
- 可选：accept 线程 + worker 处理；或多 Reactor

### Phase 4 — macOS / Windows 对齐

- 行为矩阵绿灯
- 同一套高层测试跨平台跑通

### Phase 5 — 语言糖与生态

- `async fn` / `await` 体验打磨
- http/websocket 全面 async
- 文档、示例、与「为什么做 xlang」叙事对齐

## 9. 风险与开放问题

| 风险 | 说明 | 缓解 |
| --- | --- | --- |
| 半成品 API 扩散 | 多套 pump/drain 并存 | Phase 0 收敛，旧 API 标记 deprecated |
| 取消语义不一致 | Threaded vs Evented | 文档强制写清 + 测试矩阵 |
| C glue 残留 | 与自举终局冲突 | 排进去 C 清单 |
| 过度设计 | 一次做齐 Tokio | 先 Linux 单 Reactor 打穿再扩展 |
| 学习成本 | async 染色 | 保留同步 API；async 为增量能力 |

**开放问题（需拍板）**：

1. 默认 Runtime 是单线程 Evented 还是「检测并自动选」？
2. `async` 关键字语义最终是状态机还是 CPS，还是两者并存？
3. 定时器、信号是否并入同一 Reactor（建议是）？
4. 是否提供「无运行时」嵌入式模式（只暴露 poll 接口）？

## 10. 成功标准（可验收）

- **功能**：单线程 Evented 下可跑稳定的并发 TCP 服务（万级连接量级可配置压测）
- **完整**：accept/read/write/connect 均有 async 路径，且取消/超时可用
- **平台**：Linux 主路径生产可用；macOS/Windows 功能对齐
- **纯净**：调度核心无手写 C（或仅余 sys 边界）
- **叙事**：能明确写出——「补齐了 Zig Evented 网络缺口，且保持可读与安全默认」

## 11. 结论与建议

**现在**：继续以自举为唯一主线，异步相关只做不破坏、不扩散的维护。

**自举完成后**：按本文 Phase 0→1 推进，优先 **统一 Reactor + Linux io_uring + net 全异步**，这是与项目起源最强相关、也最有差异化的一块。
