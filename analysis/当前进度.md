## wave525（已闭 · runtime_crypto_inc_glue 根因修复 xlang-c backend ABI bug + Makefile R2 thin+rest 补全 双端 L2）

| 项 | 状态 |
|----|------|
| 触发 | wave521 发现的 6 个"半残"模块之一；审计发现 xlang-c backend ABI bug |
| 模块 | `runtime_crypto_inc_glue`（357 行；SHA-256/512 + HMAC + AES/ChaCha 常量查表 + 位旋转 helper） |
| 根因 bug | **xlang-c backend calling convention bug**：xlang-c 生成的函数使用非标准 ABI（参数通过栈帧而非 AAPCS64 寄存器传递）。对 `.x → .x` 调用（双方相同 ABI）和 `.x → C` 调用（wrapper 从栈帧读参后放回寄存器再调 C）无害，但 **C → .x 调用 segfault**：C 调用方把参数放寄存器（标准 AAPCS64），.x 被调用方从栈帧读参——栈帧从未被设置过参数，读到垃圾值 → segfault |
| 暴露路径 | `xlang_sha256_block_impl`（C 函数，rest .from_x.c）调用 `xlang_sha256_rotr32`（.x wrapper，thin）——C → .x 调用。wave525 首次让包含直接逻辑的 thin .x 参与 R2 构建（之前模块都是纯转发 wrapper），暴露了这个 backend bug |
| 根修 | **在 R2 架构层修复**（非 backend 补丁）：① 将 5 个 thin .x wrapper 的直接逻辑提取为 `_impl` C 函数（始终编译在 rest）：`xlang_sha256_rotr32_impl`/`ch_impl`/`maj_impl`/`crypto_i32_sub_impl`/`crypto_rotl32_impl` ② thin .x wrapper 改为纯转发到 `_impl`（与其他 R2 模块如 compress_zlib_glue/test_fn_invoke 一致）③ `xlang_sha256_block_impl` 内部调用从 wrapper（C → .x）改为 `_impl`（C → C），消除 ABI 不匹配 |
| 构建模式 | **thin+rest**——thin (.x) 提供 6 个 `#[no_mangle]` 纯转发 wrappers；rest (.from_x.c) 提供 5 个 `_impl` C 函数（始终编译）+ `xlang_sha256_block_impl`（C → C 调用 _impl）+ C-only 函数（SHA-256/512/HMAC/AES/ChaCha/K256） |
| nm 一致性 macOS | cold vs R2：17+ 核心 T 符号对齐（6 wrappers + 5 _impl + block_impl + SHA-256/HMAC/SHA-512/AES/ChaCha/K256），仅 R2 多 `_doc_anchor` |
| nm 一致性 Ubuntu | cold vs R2：同上 17+ 核心符号对齐 |
| 产品矩阵 macOS | g-ffi-5-std-wrap ✅ · crypto 全链路 ✅（segfault 修复） |
| 产品矩阵 Ubuntu | g-ffi-5-std-wrap ✅ · crypto 全链路 ✅ |

| 关键发现 | **xlang-c backend ABI bug**：连续三波（wave523/524/525）发现 pre-existing bug。wave525 发现的是最严重的——xlang-c backend 生成的代码使用非标准 calling convention（参数通过栈帧而非寄存器），导致 C → .x 调用 segfault。修复策略：不修 backend（大工程），而在 R2 架构层规避——thin 只做转发，逻辑在 rest _impl。这符合正确的 thin+rest 模式。backend ABI bug 记录为已知问题，后续单独修复（影响所有包含直接逻辑的 .x 函数被 C 调用的场景） |
