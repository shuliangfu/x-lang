## 1. Grok 五条建议逐条评估

### 1.1 建议 #2「优先 X.O 机制」— **已实现，无需再做**

Grok 建议：在 xbuild/g05/catalog 加「优先 `*_x.o`，fallback gen.c」策略。

**本仓现状**：已实现三层：
1. `g05_ensure_relink_prereqs.sh:98` `g05_try_x_to_o()` — 22 处调用点，先 `.x → -E → .o`，失败回退 seed
2. `driver_leaf_x_to_o.sh:104` — 8 个已退役 gen 的产品 leaf 表（G.7 单权威）
3. `ensure_archaeology_gen.sh:121` — 退役 gen 的考古生产体（pin/seed/-E 三档）

**结论**：机制闭环，但仅 8 个 driver/lsp 子命令 gen 真走 PREFER_X_O 产品路径。其余 22 个仍由 `ensure_*_gen.sh` pin/seed/-E 三档管理，**产品仍读 pin 体**。瓶颈不在机制，在「哪些 gen 被纳入 catalog」。

### 1.2 建议 #1「批量处理已有 ensure 的」— **方向对，但需澄清「退役」语义**

Grok 建议：统一改成「产品路径默认用 `*_x.o`，需要时才调 ensure」。

**本仓现状**：20/22 已有 ensure 脚本，但 ensure 的作用是**维护 pin**（pin/seed/-E 三档），不是退役。真正退役 = 把 gen 从 `ensure_*_gen.sh` 管理迁移到 `driver_leaf_x_to_o.sh` catalog + `ensure_archaeology_gen.sh` 考古。

**可行做法**：对 B 层 6 个中间层 gen，批量执行「ensure → catalog 迁移」：
- 把 `lsp_diag_gen` / `lsp_io_gen` / `lsp_gen` / `driver_gen` / `preprocess_gen` / `pipeline_gen` 加入 `driver_leaf_x_to_o.sh` leaf 表
- 对应 `ensure_lsp_pipeline_gen.sh` / `ensure_driver_gen.sh` 改为考古模式（参考 `ensure_archaeology_gen.sh`）

**风险**：这 6 个 gen 的 `*_x.o` 是否稳定通过 `-E` 路径？需先验证。

### 1.3 建议 #3「按依赖关系批量清」— **合理，分层执行**

Grok 建议：先清工具链/测试，再中间层，最后前端三大件。

**本仓适配**：
- **C 层 11 个**（工具链/测试）— 无 7.4 阻塞，可先清。含双版本统一（ast_gen/gen2、token_gen/gen2、lexer_gen/gen2）。
- **B 层 6 个**（中间层）— 无 7.4 阻塞，但依赖 `pipeline_x.o` 稳定。建议第二批。
- **A 层 5 个**（前端三大件）— **7.4 硬阻塞**，必须和阶段 7.4 合并。

### 1.4 建议 #4「自动化检测残留引用」— **高价值，值得做**

Grok 建议：写脚本扫哪些地方还直接引用 `*_gen.c`、哪些 `*_x.o` 已存在但没被优先使用。

**本仓适配**：可写 `scripts/audit_gen_retirement.sh`：
1. 扫 `compiler/scripts/*.sh` 中对 `*_gen.c` 的直接引用（grep `-l '*_gen\.c'`）
2. 扫 `compiler/seeds/` 中 `*_gen.linux.x86_64.c` 是否仍被 ensure 当 fallback
3. 扫 `build_asm/` 中 `gen_driver/*.c` 残留
4. 输出：已退役（catalog 管理）/ 半退役（ensure 仍 pin）/ 未退役（无 ensure）三档清单

每次 wave 后跑，进度可视化。

### 1.5 建议 #5「大文件分两步」— **合理，前端三大件必须分步**

Grok 建议：先让产品热路径走 `*_x.o`（日常构建不读 pin），再处理冷启动/seed 路径。

**本仓适配**：对 A 层 5 个前端 gen：
- **步骤 1**：产品热路径切 `*_x.o`（日常 L2 构建不读 pin）— 需 `*_x.o` 通过 `-E` 稳定
- **步骤 2**：冷启动 seed 路径重设计 — 需阶段 7.4 mega 去 pin 完成 + 阶段 10 语言能力 L2（syscall/FFI）

**关键**：步骤 1 可独立于 7.4 推进（只要 `*_x.o` 稳定）；步骤 2 必须等 7.4。

## 2. Grok 建议低估的两个约束

### 2.1 seed pin 仍是 fallback 权威

**事实**：`ensure_migrate_gen.sh:64-100` 的 `refresh_gen_from_seed_if_stale()` 在本地 pin 不满足契约时，从 tip seed（`compiler/seeds/*.linux.x86_64.c`）覆盖。这意味着：
- 即使 gen.c 文件退役（删除/考古化），seed pin 仍是产品符号来源
- BC 层「零 cc」要求 seed 本身也退役 — 这是阶段 12（冷启动 seed 链路重设计）的工作

**影响**：Grok 建议的「批量退役」只能解决 gen.c 文件层面，不能解决 seed pin 层面。真正退役需要双轨：gen.c 退役 + seed pin 退役。

### 2.2 阶段 7.4 前端 mega 去 pin 是硬阻塞

**事实**：A 层 5 个前端 gen（parser/lexer/ast_gen2/typeck/codegen）的去 pin 依赖阶段 7.4（runtime/parser/link_abi + typeck/codegen pin 全部 ⬜ 0/5）。只要 pin seed 仍是产品符号权威，gen.c 就无法真退役。

**影响**：Grok 建议的「半个月完成」对 A 层不现实 — 7.4 本身是更大工程。A 层必须和 7.4 合并推进。

### 2.3 阶段 8.3 非 gen C 才是 BC 层主债

**事实**：`pipeline_glue` ~17.1k + `ast_pool` ~12.9k + 30+ 域切片 = ~60k LOC，远大于 22 个 gen.c 单文件总量。xbuild 要在 BC 层摆脱 host-cc，**必须先消化 8.3**。

**影响**：阶段 8（gen.c 退役）和阶段 8.3（非 gen C 迁移）是**并行轨道**，不是串行。当前 wave1035 在做 8.3.1，阶段 8 可同步推进 B/C 层。

## 3. 高效路径设计

### 3.1 核心原则

1. **不照搬 Grok**：机制已存在，瓶颈在「纳入 catalog」而非「建机制」
2. **分批次独立推进**：B/C 层无 7.4 阻塞，可与 8.3.1 并行
3. **A 层合并 7.4**：前端三大件不单独退役，和 7.4 mega 去 pin 一起打
4. **自动化兜底**：写审计脚本，每次 wave 后跑
5. **双版本统一先行**：ast_gen/gen2、token_gen/gen2、lexer_gen/gen2 统一是独立工作，无依赖

### 3.2 批次划分

> **修正（2026-08-01）**：经核实，三对「双版本」均非 G.7 违规双权威：
> - `ast_gen.c`(无前缀,stage1) vs `ast_gen2.c`(ast_前缀,产品/stage2)：同源不同生成模式（`-x` 标志），不可合并
> - `token_gen.c`(最小提取,stage1) vs `token_gen2.c`(完整展开,stage2)：同源不同展开深度，不可合并
> - `lexer_gen.c`(产品权威) vs `lexer_gen2.c`(0字节空壳,stage2)：角色不同，lexer_gen2.c 可删除
>
> 批次 0 实际可做：删除空壳 + 孤立 stale seed pins。

## 4. 自动化审计脚本设计

### 4.1 `scripts/audit_gen_retirement.sh` 规格

```bash
#!/bin/bash
# 审计 gen.c 退役状态：已退役 / 半退役 / 未退役
# 输出三档清单 + 进度统计

# 1. 已退役：在 driver_leaf_x_to_o.sh catalog 中
# 2. 半退役：有 ensure 脚本但仍 pin/seed/-E 管理
# 3. 未退役：无 ensure 脚本或无 *_x.o

# 输入：compiler/*.c 中 *_gen.c 文件列表
# 输出：
#   [RETIRED] driver_fmt_gen.c → driver_fmt_x.o (catalog)
#   [HALF]    lsp_diag_gen.c → lsp_diag_x.o (ensure_lsp_pipeline_gen.sh)
#   [PINNED]  parser_gen.c → parser_x.o (ensure_migrate_gen.sh, 7.4 blocked)
#   [DUAL]    ast_gen.c + ast_gen2.c (双版本需统一)
#   ...
#   Summary: 8 retired / 14 half / 8 pinned / 3 dual
```

### 4.2 检测项

1. **catalog 覆盖**：`driver_leaf_x_to_o.sh` 中是否有对应 leaf
2. **ensure 脚本**：哪个 `ensure_*_gen.sh` 管理此 gen
3. **`*_x.o` 存在性**：`compiler/*_x.o` 是否存在
4. **seed pin**：`compiler/seeds/*_gen.linux.x86_64.c` 是否仍被 `refresh_gen_from_seed_if_stale` 引用
5. **双版本**：是否存在 `*_gen.c` + `*_gen2.c` 并存
6. **7.4 阻塞**：是否属于 A 层前端三大件

## 5. 效率对比与时间预估

| 方式 | 预估工作量 | 说明 |
|------|-----------|------|
| 传统逐个手动退役 | 2-3 周 | 慢，容易反复 |
| Grok 建议（全盘照搬） | 7-12 天 | 低估 seed pin + 7.4 阻塞 |
| **本方案（分批次 + 7.4 合并 + 自动化）** | **批次 0+1+2: 3-5 天 · 批次 3: 等 7.4** | 可与 8.3 并行，风险可控 |

### 5.1 为什么不照搬 Grok

1. Grok 建议 #2（优先 X.O 机制）已实现，重复投入无收益
2. Grok 未识别 seed pin 仍是 fallback 权威 — 批量退役 gen.c 不等于 BC 层零 cc
3. Grok 未识别 7.4 硬阻塞 — A 层 5 个无法在 7.4 完成前退役
4. Grok 未识别 8.3 非 gen C 才是主债 — 阶段 8 和 8.3 应并行而非串行

### 5.2 本方案的优势

1. **批次 0+1+2 可立即启动**，与 8.3.1 并行，不阻塞当前 wave 流
2. **批次 3 合并 7.4**，避免重复工作
3. **自动化审计**贯穿全程，进度可视化
4. **双版本统一先行**，消除 G.7 双权威债

## 7. 风险与回退

### 7.1 风险

1. **`*_x.o` 通过 `-E` 不稳定**：某些 gen 的 `.x` 源可能依赖宏/条件编译，`-E` 展开后语法变化
   - 缓解：批次 1/2 每个都先 L2 双端验证
2. **seed pin 退役过早**：冷启动路径断链
   - 缓解：seed pin 退役必须等阶段 12，不在阶段 8 处理
3. **双版本统一误删**：ast_gen.c vs ast_gen2.c 语义可能不同
   - 缓解：先 diff 两者，确认差异后再合并

### 7.2 回退

- 每个批次独立 commit，失败时 `git revert` 单批
- catalog 迁移可回退（从 `driver_leaf_x_to_o.sh` 移除即可）
- ensure 脚本改考古模式可回退（恢复 pin/seed/-E 三档）

## 8. 结论

Grok 建议的方向正确（分批 + 自动化），但低估了本仓的两个约束（seed pin + 7.4 阻塞）。本方案修正后：

- **批次 0+1+2 可与 8.3.1 并行**，3-5 天完成 17 个 gen 退役
- **批次 3 合并 7.4**，避免重复工作
- **自动化审计**贯穿全程

核心洞察：**阶段 8（gen.c 退役）不是 BC 层零 cc 的关键路径** — 阶段 8.3（非 gen C ~60k LOC）才是主债。阶段 8 应与 8.3 并行推进，而非串行等待。
