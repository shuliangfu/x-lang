# xlang 性能基准对比测试分析

**文档版本**：v1.1（2026-07-31）
**日期**：2026-07-31
**状态**：设计草案（自举完成后落地实现与门禁）
**对比对象**：C（clang -O2 / -O3 为主锚）、Zig（ReleaseFast / ReleaseSafe）
**目的**：把「高性能 / 默认逼近或超过 careful C」从口号变成可复现、可回归的工程标准
**原则**：同算法、同输入、同机器、可脚本化；禁止只报最好一次

> **与现有 perf 体系的关系（v1.1 新增）**：本文是**总纲与对照框架**，不是从零建 bench。项目已有成熟体系——`tests/bench/`（40+ 三语言基准源码）、`tests/run-perf-*.sh`（30+ perf 脚本，含 Zig 对照门禁）、`tests/baseline/*.tsv`（回归门禁基线）、`analysis/archive/perf/`（15+ 专项分析，含 [perf-vs-zig-baseline.md](archive/perf/perf-vs-zig-baseline.md) 与 [perf-zig-strategy-dashboard-v1.md](archive/perf/perf-zig-strategy-dashboard-v1.md)）。本文的作用是：(1) 给散落的专项基准一个统一维度对照清单；(2) 补齐尚未覆盖的维度；(3) 统一公平性与叙事规则。§3 与 §2 各维度的「现有对应」列说明映射，**禁止另起 bench/ 重复造**。

## 0. 一句话结论

| 对比轴 | 主锚 | 次锚 | xlang 成功标准（建议） |
| --- | --- | --- | --- |
| 运行时热核 | 同算法 C + clang -O2 | Zig ReleaseFast | Fast 路径 ≥ 0.95× C，目标 ≥ 1.0× C |
| 二进制体积 | C stripped | Zig stripped | 同量级 C，不系统性大于 Zig |
| 编译时间 | clang | Zig | 可接受；大项目不系统性差于 Zig 一个数量级 |
| 安全子集开销 | C（无检查） | Zig ReleaseSafe / Safety | 可选检查的开销可量化、可关闭 |
| 异步 / 网络 | 手写 io_uring C | Zig std.Io / 社区库 | 自举后 Evented 路径有独立矩阵（见 [async-platform-matrix.md](async-platform-matrix.md)） |

**C 是正确性与极限的尺子；Zig 是同代系统语言的产品对照。**

## 1. 对比哲学与公平性规则

### 1.1 为什么是 C + Zig

| 对象 | 角色 |
| --- | --- |
| C + clang | 工业默认的「careful C」上限；xlang 文档已用它做主锚（与 x-jsc 合约一致） |
| Zig | 最直接的同定位对手：无 GC、可交叉编译、显式内存、追求简单与性能 |
| （可选后期）Rust | 安全模型对照，不作为 v1 主对比，避免故事发散 |

### 1.2 公平对比硬规则

- 同算法、同数据结构、同输入规模（禁止语言习惯性「换算法偷赢」）
- 同一台机器、绑核、关睿频策略写进脚本（或明确记录）
- 编译选项固定并文档化（见 §1.3）
- 多次运行 + 统计（median / mean / p95，禁止只贴最快一次）
- 源码公开在 `tests/bench/`，可一键复现
- xlang 安全特性若引入额外检查，必须有「检查开 / 检查关」两列
- 禁止用不同优化级别的二进制互相偷比

**统计严谨性补充（v1.1）**：

- **预热（warmup）**：冷启动第一轮丢弃，至少 1–2 轮 warmup 后再开始采样（冷启动受 page fault / icache 冷启动污染）。
- **最小样本量**：每个 case 至少 10 次有效采样；方差大（CV > 5%）时自适应加到 30 次。hyperfine 默认 10，项目脚本（如 `run-perf-async.sh`）已有 `RUNS` / `ROUNDS` 参数，需统一最小值。
- **噪声控制**：CPU governor 设 `performance`（`cpupower frequency-set -g performance`）、关 ASLR 或记录其影响、清后台进程、记录环境温度/散热状态。`tests/lib/` 应提供一个 `pin_cpu.sh` 等价的环境固化 helper。
- **离群判定**：丢弃 > 3σ 的采样点并在原始 JSON 中保留标记，不得静默删除。

### 1.3 推荐工具链配置（基线）

| 语言 | 推荐配置 | 说明 |
| --- | --- | --- |
| C | clang -O2 -flto 与 clang -O3 -flto 两档 | -O2 为主锚（与 x-jsc 合约一致）；-O3 为冲击档 |
| C 备选 | gcc -O2 -flto | 防止「只打 clang」被质疑 |
| Zig | -OReleaseFast、-OReleaseSafe | Fast 对性能；Safe 对安全开销 |
| xlang | 产品默认优化档 + 显式「安全检查开/关」 | 名称在实现期写入 perf_contract |

**版本基线（v1.1 新增，须锁定写入报告）**：

| 工具 | 基线版本 | 来源 |
| --- | --- | --- |
| clang | ≥ 14（macOS arm64 用 Apple clang，Ubuntu x86_64 用 LLVM clang） | 项目硬规范 |
| Zig | **0.13.0**（现有基线，见 [perf-zig-baseline-v1.md](archive/perf/perf-zig-baseline-v1.md)） | 已定版，median 列由 Linux x86_64 + zig 0.13.0 `--record` 填充 |
| Zig（异步参考） | 0.16 方向 | 仅作异步架构抽象参考（见 [全面异步架构-分析与准备.md](全面异步架构-分析与准备.md)），**不参与 v1 性能对比**，避免版本混谈 |

> **注意**：Zig 0.13.0 是性能基线锚；0.16 仅用于异步叙事对照。两版本不得混入同一张对比表。

统一：strip 后比体积；链接策略（静态/动态 libc）必须三方一致或分表说明。

## 2. 完整对比维度清单

下面按 P0（必须）→ P1（重要）→ P2（扩展）列出。自举后先做 P0，再铺 P1。

> **编号说明（v1.1 修正）**：原稿用 `C01`/`P01` 与语言名 `C`、优先级 `P0` 视觉冲突，已改为：编译时间 `BT01`（Build Time）、并发 `CC01`（ConCurrency）。其余前缀：R=Runtime、M=Memory、B=Binary、S=Safety、A=ABI、I=IO、E=Embedded、L=Language-self。每项「现有对应」列映射到已有资产，无则标「待补」。

### 2.1 P0 — 运行时计算性能（主战场）

目标：证明 codegen + 优化能打到 careful C。

| 编号 | 场景 | 测什么 | 对比意义 | 现有对应 |
| --- | --- | --- | --- | --- |
| R01 | 整数算术热循环 | 吞吐 / cycle | 基础 isel、强度削减 | 待补 |
| R02 | 浮点算术 / 累加 | 吞吐、数值稳定性说明 | FP 与 FMA | 待补 |
| R03 | 数组遍历 + 规约 | GB/s、IPC | 边界检查开销是否可消 | `dod_soa_sum_x.x` / `dod_f32_soa_sum_x.x` / `run-perf-dod-soa.sh` |
| R04 | 手工 SIMD vs 自动向量化 | 相对 C/Zig vector | 向量化能力 | `simd_dot.*` / `run-perf-simd-dot.sh`、`run-perf-simd-shuffle-select.sh` |
| R05 | 矩阵乘（小/中） | GFLOPS | 寄存器、缓存、内联 | 待补 |
| R06 | 排序（如 qsort 同类算法） | 时间 | 分支、比较、调用 | 待补 |
| R07 | 哈希（固定算法，如 xxHash 类） | GB/s | 位操作、内存访问 | 待补 |
| R08 | 字符串扫描 / 查找 | GB/s | 内存与分支 | `string_arena_concat.x` / `run-perf-string-arena.sh`（部分） |
| R09 | 递归 vs 迭代（同算法） | 时间、栈 | 调用约定、尾调用 | 待补 |
| R10 | 结构体密集操作 | 时间 | ABI、布局、别名 | `struct_param.*` / `call_boundary.*` |

**成功标准（建议写入合约）**：

- Fast / 检查关闭：median 时间 ≤ 1.05 × C(-O2)，冲刺目标 ≤ 1.00 × C(-O2)
- 对 Zig ReleaseFast：不系统性落后；允许单项来回赢

## 4. 指标与采集

| 指标 | 工具建议 | 备注 |
| --- | --- | --- |
| wall time | hyperfine 或自写多轮 | 主报告用 median |
| CPU cycles / instructions | perf stat | 解释「为什么慢」 |
| 缓存/分支 | perf LLC / branch-misses | 优化方向 |
| RSS / 高水位 | /usr/bin/time -v 或 cgroup | 内存 |
| 二进制体积 | size、ls -l stripped | 分段 text/data 更佳 |
| 编译时间 | 干净环境多次 | 含/不含依赖下载要分开 |

**报告模板字段**：`case, lang, opt_level, safety, n, median_ms, stddev, vs_c_ratio, vs_zig_ratio`

> 现有脚本已用 `median ≤ baseline.tsv` 做门禁（如 `run-perf-async.sh` 的 `XLANG_PERF_FAIL_ON_ASYNC_REGRESSION=1`）。报告生成器应消费这些 tsv，不重复采集。

## 5. 分层成功标准（建议写进 perf_contract）

### 5.1 自举刚完成（门禁级）

- P0 微基准矩阵可跑、可出表
- 至少 80% 的 R 系列：xlang(Fast) ≤ 1.15 × C(-O2)
- hello 体积与 C 同量级有解释

### 5.2 产品叙事级（对外可讲）

- ≥ 90% R 系列：≤ 1.05 × C(-O2)
- 若干项 ≥ 1.0 × C（持平或更快）
- 与 Zig ReleaseFast 互有胜负，无大面积崩盘
- I/O 高并发有 Linux 主路径数据（对应 [perf-zig-strategy-dashboard-v1.md](archive/perf/perf-zig-strategy-dashboard-v1.md) PERF-011）

### 5.3 极致冲击级（长期）

- 关键热核稳定 ≥ C(-O2)，部分逼近/超过 C(-O3)
- 安全检查开的开销曲线清晰
- Evented 网络不低于优质 C 基线

## 6. 与 Zig 对比时的特别注意点

| 建议 | 说明 |
| --- | --- |
| Zig 默认优化与 panic 策略 | 分 ReleaseFast / ReleaseSafe 两列，勿混谈 |
| comptime 与「零成本」 | 同算法运行时比；不要把 comptime 算力偷换进运行时赢面 |
| 标准库 I/O | 异步网络以双方都能实现的子集为准，避免打半成品 API |
| 二进制体积 | 统一 strip、统一是否链接 libm/libpthread |
| 编译时间 | Zig 单编译单元 vs C 多 TU：在报告中注明工程结构差异 |
| 版本锁定 | **0.13.0 为性能基线**（见 §1.3）；0.16 仅异步叙事，不进性能表 |

---

## 7. 与 C 对比时的特别注意点

| 建议 | 说明 |
| --- | --- |
| 「careful C」 | 允许 C 写满优化（restrict、对齐、明确 inline），但禁止换更优算法 |
| UB | C 若依赖 UB「更快」，记录在案；xlang 不以 UB 换速度 |
| libc | 字符串/堆若走 libc，三方一致；比分配器时用各自默认堆并注明 |
| LTO | 主表固定有无 LTO；可附表 LTO on/off |

## 8. 门禁与 CI 建议

| 级别 | 内容 | 是否进默认 CI |
| --- | --- | --- |
| smoke | 子集 micro 不超时、比值不极端回退 | 是 |
| nightly | 全 P0 + 体积 + 编译时间 | 是（nightly） |
| release | 全 P0+P1 + 生成对比报告 | 发版前 |
| manual | 高并发 I/O、PMC 深挖 | 人工/专项 |

**回退策略**：相对基线 > 10% 变慢且无 issue 说明 → 红灯。

> **现有实现**：项目已落地 `XLANG_PERF_FAIL_ON_*_REGRESSION=1` + `tests/baseline/*.tsv` 的 median 回归门禁（async / iocp / alloc-hotspot / cache-miss / coldstart 等多个专项）。本节是把它**统一化、补齐 P0 全维度**，而非从零搭。

## 11. 风险

| 风险 | 缓解 |
| --- | --- |
| 基准被指责不公平 | 源码三方公开、选项写死、接受社区复现 |
| 过早优化编译器 | 先门禁「不严重慢于 C」，再冲刺单项 |
| 维度过多做不完 | 严格按 P0→P1→P2；P0 未绿不开 P2 |
| Zig API 变更 | 锁定 Zig 版本号写入报告（0.13.0） |
| 把 x-jsc 的 JS 基准混进来 | 分开：本文是 xlang 语言/运行时；JS 引擎另用 perf_contract |
| **编号体系冲突（v1.1 新增）** | 现有脚本用 `PERF-0xx`/`B-xxx`/`IO-x` 语义编号；本文 R/M/B/S/A/CC/I/E/L 维度编号是**对照清单**，落地时必须与现有 `PERF-0xx` 建立映射表，禁止两套编号各跑各的 |
| **安全检查开关未定义（v1.1 新增）** | S 系列依赖「xlang 安全检查开/关」是编译开关还是运行时开关——这是前置依赖，须在 std 设计先定，否则 S 系列无法测 |
| **与现有 perf 体系重复（v1.1 新增）** | §3 已明确不另起 bench/；落地时任何新基准先查 `tests/bench/` 与 `run-perf-*.sh` 是否已有 |
