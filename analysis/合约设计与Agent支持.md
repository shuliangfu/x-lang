## 0. 一句话结论

| 问题 | 结论 |
|------|------|
| **合约设计**要做什么？ | 在接口上把「调用前必须满足什么 / 返回后保证什么 / 对象始终保持什么」写成**可检查的意图**；编译器负责插入检查，**不是**再发明一套形式化验证语言。 |
| **Agent 支持**要做什么？ | 让 AI 写/改/验 `.x` 时**少幻觉、闭环快、错误可自动消化**——靠 **CLI + LSP + MCP + Skills + 诊断**，不是靠把整本手册塞进 prompt。 |
| 现在要不要做语言级 DbC？ | **不要**。自举未完成；check 闸门暂停；主航道仍是 BC residual。本稿只钉**语义与分层**，实现挂**自举后**。 |
| X 有没有「合约」？ | **有多种已存在、但名字易混的「契约」**（见 §1）。**没有**语言级 `requires` / `ensures` / `invariant`。 |
| 差异化机会在哪？ | 轻量 DbC + 已有 typeck 安全 + 一流 Agent 闭环；**禁止**做成第二套 typeck 或 Dafny 级证明器抢主线。 |

**成功标准（语言优化轨，自举后验收）：**

1. 人/AI 能在接口上写出**意图**（注释 → 库断言 → 可选语言属性），并有**统一检查策略**（debug 开 / release 默认可关）。  
2. Agent 在「只装 xlang + 官方 Skill/MCP」下能 **scaffold → 写 → check/build → explain → 改**，不必背完整手册。  
3. 与 `docs/`、typeck、codegen **单权威**；禁止再开「给 AI 的假语法」。

## 1. 先消歧：「合约 / 契约」在本仓指什么

本仓多处出现 *contract*，**含义不同**。讨论「合约设计」时必须说清层，否则会和自举工程债缠在一起。

| 名称 | 是什么 | 是否 DbC | 权威位置 |
|------|--------|----------|----------|
| **TU 符号合同** | thin/seed 单编译单元的导出符号与职责边界 | 否 | `analysis/tu_contracts/` · `archive/tu_contracts/` |
| **内存 / ABI 契约** | 布局、调用约定、region/slice、零 libc 产品约定 | 否（偏规格） | `内存契约.md` · `ABI与布局.md` · `零libc产品策略.md` |
| **docblock 契约** | G.9：每个 `.x` 方法英文 JSDoc（`@param` / 空指针 / cap / PLATFORM） | **文档级**，编译器不检查 | `AGENTS.md` · skill G.9 · 现有 `std/` / `compiler/**/*.x` |
| **运行时断言** | `core.debug.assert` / `debug_assert` / `assert_eq_*` + `panic` | **手写检查**，非接口级 DbC | `core/debug/mod.x` |
| **typeck 安全门** | region、linear、borrow、unsafe 边界、越界相关硬拒 | **编译期证明**，不是用户写的 requires | `安全路线.md` 与 typeck |
| **Design by Contract（本文主体）** | 接口上的 pre / post / invariant，编译器按模式插入检查 | **目标特性** | **未实现**（本文件路线图） |

> **口诀**：工程契约（TU/ABI/pin）≠ 文档契约（G.9）≠ 安全证明（typeck）≠ **DbC 语言特性**。  
> 后面「合约设计」**默认只指 DbC 语言/库层**，除非显式写「工程契约」。

## 2. 项目现状（与语言优化相关的真值）

### 2.1 语言定位（已定）

- **系统级、命令式、无 GC**；安全子集默认 + 显式 `unsafe`。  
- 目标：**简单 + 安全 + 高性能**（「三高一低」），学习曲线以天计。  
- 字段访问源语言**只有 `.`**（无 `->`）。  
- 切片是 `T[]`（带长度），不是伪代码里的 `[]u8`。  
- 属性已是 **`#[attr(...)]` 族**（`#[cfg]`、`#[no_mangle]`、`#[repr(C)]`、`#[inline(...)]`、内核属性等），**不是** Java 式 `@Attr` 或 Rust 宏 `#[requires]` 以外的新前缀。

### 2.2 自举与工具链（2026-08 前后）

| 项 | 现状 |
|----|------|
| 自举 | **未完成**（冷启动仍有 seed / host-cc residual；BC 🟡） |
| 产品钉盘 | 见 `自举进度.md`（L4 + 双端 bstrict 放行钉盘与 tip 安全网分离） |
| `xlang check` | **自举期暂停作闸门**（2026-08-05）；命令仍在，不抢 residual |
| LSP | 有基础路径；definition/references/hover **半实现**，完善默认 **自举后**（见 LSP 分析文） |
| MCP / 官方 Skills | **有完整分析稿**，**未**作为产品默认交付大落地 |
| fmt / explain / test | CLI 面已有或部分规划；体验打磨挂 P1/P2 |

### 2.3 已经「像合约」但不是 DbC 的能力

这些是语言优化时**应优先复用/加强**的地基，而不是推倒重来：

| 能力 | 对 AI / 正确性的价值 | 缺口 |
|------|----------------------|------|
| **类型 + 显式返回类型** | 强制写清接口形状；无「猜类型」 | 无语言级 string 等仍在后自举缺口表 |
| **`T[]` + region** | 边界与逃逸由 typeck 管一部分 | 不能表达任意业务不变量 |
| **Option / Result（库路径）** | 错误与可空显式 | 易被 Agent 绕回裸指针 |
| **`unsafe { }`** | 危险边界可 grep | 体内无自动 pre/post |
| **G.9 英文 docblock** | Agent few-shot 与将来 `xlang doc` | **不执行**；与实现易漂移 |
| **`assert` / `panic`** | 可手写检查 | 散落函数体；无统一入口/出口语义；debug/release 开关未做成语言级 |
| **诊断码 + `explain`** | Agent 修错入口 | 需结构化 JSON/稳定字段；文案持续打磨 |
| **export / 模块边界** | 公开 API 可见 | 未绑定「公开 API 必须带合约」策略 |

### 2.4 旧稿问题（为何要重写）

| 旧稿问题 | 实际 |
|----------|------|
| 对话体、重复 Q&A | 不便当路线图 |
| 伪语法：`[]u8`、`@requires`、签名外自由挂 requires | X 是 `T[]`、`*u8`、`#[...]` |
| 未对齐已有属性 / assert / typeck | 会重复造轮子或双权威 |
| Agent 一节过泛（「要 LSP、要 fmt」） | 仓内已有 MCP/Skills/LSP 专项文 |
| 未钉**时机** | 自举前实现 DbC 会撞 parser/typeck residual |

## 3. 合约设计（Design by Contract）是什么

### 3.1 定义（工程可用版）

**合约** = 写在**接口**上的精确承诺，由工具统一检查：

| 种类 | 检查时机 | 回答的问题 | 例子（语义，非最终语法） |
|------|----------|------------|--------------------------|
| **前置条件 Pre** | 函数入口 | 调用方保证了什么？ | `len > 0`、`ptr != null`、`start <= end` |
| **后置条件 Post** | 所有返回路径出口 | 实现方保证了什么？ | `result == a + b`、缓冲区前 `n` 字节已写 |
| **不变量 Inv** | 类型公开方法进/出 | 对象是否始终合法？ | `len <= capacity` |

- **谁写内容**：人、AI、或从测试/规格生成——**编译器不会凭空猜业务意图**。  
- **谁插入检查**：编译器/库在入口与出口**自动**插桩（相对「每个调用点手写 if」）。  
- **不是**：完整形式化验证（Dafny/SPARK 级证明）——那是可选远期，**非 v1 目标**。

### 3.2 为什么对 X 有价值

1. **AI 生成代码**：模型擅长「看起来对」；合约把意图钉死，检查暴露漏边界。  
2. **与 typeck 互补**：typeck 管内存/借用等**可静态证明**的类；合约管**业务与容量**（`path_len < 512`）等证明器不愿全包的部分。  
3. **与 G.9 互补**：注释是给人/文档的；可执行合约是给编译器/CI 的。理想路径是 **docblock ↔ 属性同源**，避免第三权威。  
4. **性能叙事兼容**：主流做法是 **debug/测试开检查，release 默认关**（见 §3.5）；不违背「默认快」。

### 3.3 主流语言对照（2026 现实）

| 语言 | 合约形态 | 备注 |
|------|----------|------|
| Eiffel | 语言原生 DbC | 发源地 |
| Ada / SPARK | 原生 + 可升级证明 | 安全关键 |
| D | `in` / `out` / `invariant` | 系统语言先例 |
| C++26 | 标准合约 | 语义可配置（enforce/ignore…） |
| Rust | 无语言级；crate / 证明工具 | 靠类型 + `debug_assert!` |
| Go / Java / Python / TS | 库或注解为主 | 非一等公民 |
| C | 宏/assert | 无接口级 |

**对 X 的含义**：系统语言里做**轻量、可开关**的 DbC 仍是差异化；但必须长得像 **X 的 `#[...]`**，且**先库后语言**，避免自举期炸 parser。

### 3.4 性能：会不会拖垮「默认快」？

| 模式 | 行为 | 场景 |
|------|------|------|
| **Debug / 测试 / CI** | 插桩执行 pre/post/inv | 开发、Agent 闭环、bstrict 子集 |
| **Release 默认** | 去掉运行时检查（零/近零开销） | 产品发布 |
| **Release 保留关键** | 属性标记「此条 enforce」 | 安全边界、不可信输入 |
| **静态能证则不插** | typeck/opt 已证明的条件可省略 | 与 BCE 等优化同向 |

原则：**合约默认不向 release 热路径收税**；需要永久检查的必须**显式 opt-in**。

### 3.5 和「手写 if / assert」的差别

| | 手写 `if` / `assert` | DbC |
|--|---------------------|-----|
| 写在哪 | 函数体或调用点 | 接口（属性 / contract 块） |
| 谁保证全路径 | 作者自己 | 编译器在所有 return 路径插 post |
| 开关 | 各自为政 | 统一构建语义 |
| 对 AI | 易漏、易被「优化掉」写错位置 | 先读接口再生成体 |
| 文档 | 易与实现分叉 | 可生成进 `xlang doc` |

## 4. X 语言上的合约：分层落地（推荐）

> **铁律**：同一语义只许**一条权威**（G.7）。先强化现有层，再加语法；禁止「注释一套、属性一套、宏一套」长期分叉。

### 4.1 四层模型

```text
L0  文档合约（已有）     G.9 docblock：意图给人 / Agent / 将来 xlang doc
L1  库级可执行合约       core.contract 或强化 core.debug：入口/出口辅助 + 构建 cfg
L2  语言级轻量 DbC       #[requires]/#[ensures]/#[invariant] 或 contract { }（parser+typeck+codegen）
L3  可选静态加强         能证的在 typeck 证明；证不出保留 L1/L2 运行时（非完整证明器）
```

| 层 | 自举前 | 自举后建议窗口 | 说明 |
|----|--------|----------------|------|
| **L0** | **继续做** | 持续 | 已强制；触碰旧中文 docblock 时英文化 |
| **L1** | 可**小步**准备（不碰 parser 主路径） | **P1–P2a 早期** | 纯库 + `cfg(debug)`；立刻服务 Agent/测试 |
| **L2** | **禁止**（parser/typeck 风险） | **P2a 语言 + 诊断** 或其后专门波次 | 须 RFC + 金标用例 + 双端 |
| **L3** | 不做 | **P3+ 可选** | 仅在 L2 稳定且不伤吞吐时 |

### 4.2 语法草案（贴合 X，**非冻结**）

旧稿推荐 `@requires`。X **已统一 `#[...]`**，草案改为属性族，与 `#[cfg]` / `#[no_mangle]` 一致。

**方案 A（首选方向）：属性挂在声明上**

```x
/**
 * Copy src[0..n) into dst. Caller guarantees dst capacity.
 * @param dst *u8 — destination; non-null
 * @param src *u8 — source; non-null
 * @param n i32 — byte count; n >= 0
 * @return i32 — 0 success, -1 failure
 * PLATFORM: SHARED
 */
#[requires(dst != null)]
#[requires(src != null)]
#[requires(n >= 0)]
#[ensures(result == 0 || result == -1)]
export function copy_n(dst: *u8, src: *u8, n: i32): i32 {
  // implementation
  return 0;
}

#[invariant(self.len <= self.capacity)]
struct Buf {
  data: *u8;
  len: i32;
  capacity: i32;
}
```

**方案 B：`contract { }` 块（次选，接口仍外置）**

```x
export function copy_n(dst: *u8, src: *u8, n: i32): i32
contract {
  requires(dst != null);
  requires(src != null);
  requires(n >= 0);
  ensures(result == 0 || result == -1);
}
{
  return 0;
}
```

**明确不推荐（旧对话中的体内堆 requires）**

```x
// 不推荐：ensures 语义变成「延迟到出口」却写在体首，易与普通语句混淆
function copy_n(...) {
  requires(...);  // 看起来像普通调用
  ensures(...);
  ...
}
```

### 4.3 语义设计要点（实现前必须钉死）

| 议题 | 建议默认 |
|------|----------|
| **表达式能力** | v1 仅：比较、逻辑与/或、字段、`null`、`old(expr)`（post 用）、`result`；**禁止**任意副作用调用 |
| **失败行为** | debug：`panic` 或结构化 abort；可选「观察模式」只诊断不杀进程（二期） |
| **公开 vs 私有** | 默认：`export` / 公开方法检查 inv；私有辅助可跳过 inv（可配置） |
| **unsafe** | unsafe 体内仍可声明合约；**不能**用合约代替 `unsafe` 审核 |
| **与 typeck** | 合约**不能**放宽 borrow/region 硬拒；只能多加检查 |
| **泛型** | v1 可只支持单态后的具体函数；泛型合约随 monomorph 复制 |
| **平台** | `PLATFORM: SHARED` 语义；检查插入在 SHARED codegen 路径，双端验 |

### 4.4 L1 库级最小面（可先于语法）

在**不改 parser** 的前提下，可先提供（名称可再议，须全库唯一权威）：

```x
// 示意：库 API，非最终定名
// core.contract 或 core.debug 扩展
export function require(cond: bool, msg: *u8): void;   // 入口辅助
export function ensure(cond: bool, msg: *u8): void;    // 作者在 return 前调用（L1 弱于 L2）
```

L1 的局限：post 仍靠作者/AI 在每条 return 前记得调用——这正是 L2 要解决的。  
因此 L1 定位是 **过渡与教育**，不是终局。

### 4.5 与现有 `core.debug` 的关系

当前 `assert` / `debug_assert` 在失败时 `panic()`，且二者实现**几乎相同**（未见真正的 cfg 剥离）。自举后优化时：

1. **理清** `assert`（可配置）vs `debug_assert`（仅 debug）的构建语义；  
2. 合约检查**复用**同一失败路径（禁止第三套 abort）；  
3. G.7：扩展现有权威，禁止再写 `contract_assert_v2`。

## 5. Agent 支持是什么（贴合本仓）

### 5.1 定义

**Agent 支持** = 让 Cursor / Claude Code / Grok / 自研 agent 等在 **写、改、编译、修、测** X 代码时：

- **正确率更高**（少用 Rust/Go 幻觉）；  
- **闭环更快**（诊断准、编译反馈可用）；  
- **纪律可加载**（Skills / AGENTS，而不是每次会话重教）。

它**不是**「再做一个聊天机器人」，而是 **编译器产品面 + 协议 + 流程说明书**。

### 5.2 分层架构（已在专项文中定调）

```text
┌─────────────────────────────────────────────────────────┐
│  Skills / AGENTS.md     行为剧本：何时查、何时验、禁区   │
├─────────────────────────────────────────────────────────┤
│  MCP (xlang --mcp)      Agent 工具：check/explain/std…  │
│  LSP (xlang --lsp)      人机 IDE：跳转/补全/诊断波浪线    │
├─────────────────────────────────────────────────────────┤
│  CLI                    build / check / fmt / test / doc │
├─────────────────────────────────────────────────────────┤
│  编译器权威             parser · typeck · diag · codegen │
│  文档真源               docs/*.md ·（将来）从 G.9 抽 doc  │
└─────────────────────────────────────────────────────────┘
```

| 层 | 解决什么 | 仓内状态 |
|----|----------|----------|
| **真源知识** | 语法/std「是什么」 | `docs/` 较全；与实现对照表有；易漂移处要盯 |
| **真能力** | 查/编/解释 | CLI 有；MCP **分析已有、产品化后做**；LSP 半实现 |
| **行为剧本** | 何时用工具、禁止幻觉 | 实现者 skill 强；**应用向官方 Skills 仍缺** |
| **合约（DbC）** | 意图可检查 | **未做**；与 Agent 生成「先合约后实现」强相关 |

详细工具清单见：[`xlang-mcp-服务分析.md`](./xlang-mcp-服务分析.md)、[`xlang-官方Skills分析.md`](./xlang-官方Skills分析.md)。  
**禁止**在本文再复制一套 Tools 表（防双权威）。

### 5.3 Agent 需要的编译器能力（优先级）

| 优先级 | 能力 | 为何 | 时机建议 |
|--------|------|------|----------|
| **P0** | 稳定 **结构化诊断**（文件、行列、code、消息） | Agent 自动改的前提 | 自举后 P1/P2a；与 `explain` 对齐 |
| **P0** | **`check` / `build` 诚实、快** | 闭环；假绿会教坏模型 | 自举完成后恢复 check 闸门策略 |
| **P1** | **`explain CODE`** 机器可读 | 少猜 | P1 CLI 打磨 |
| **P1** | **fmt** 幂等 | 降风格噪声 | P1 |
| **P1** | **官方 Skills（应用轨）** | 禁 `->`/`fn`、小步+必验 | 可与 MCP 同波准备文案 |
| **P1** | **MCP 最小工具集** | overview / check / explain / scaffold | 自举后；分析稿已有 |
| **P2** | LSP definition/references/hover 做满 | 人机；Agent 也可间接受益 | 见 LSP 分析文决策 |
| **P2** | **L0 合约质量**（std 关键 API docblock） | few-shot 真源 | 持续；与 std 清单同步 |
| **P3** | **L1/L2 DbC** | 「先写意图再实现」工业化 | 见 §4 / §6 |

### 5.4 本仓已有、Agent 已在用的纪律（不要推倒）

改语言/优化时，Agent **实现者轨**已有强制纪律，语言特性必须**兼容**而非冲突：

- 根源治理、单权威、seed/.x 同 commit  
- 字段只有 `.`  
- G.9 英文注释  
- Ubuntu 金标、L4 真冷、双端 SHARED  
- 自举期不默认跑 check  

应用轨 Skills 必须与上述 **分轨**（官方 Skills 分析已强调：禁止把 L4 全擦写进「新建 hello 服务」）。

### 5.5 Agent × 合约：推荐工作流（自举后）

```text
1. 人/规格：公开 API 写 L0 docblock（必做）
2. 可选：L1 require / 将来 L2 #[requires]/#[ensures]
3. Agent：只读接口 + docs/MCP → 生成函数体
4. xlang check / build（debug 合约开）
5. 失败 → explain + 结构化 diag → 只改实现或修正过严合约
6. 测试 / 相关 bstrict 或 xlang test
7. release 构建：默认剥离检查；关键项显式保留
```

这比「生成 200 行再人肉找越界」更适合模型。

## 7. 语言优化总原则（合约 + Agent 共用）

1. **意图上提、检查下沉**：人/AI 写意图；编译器/库负责检查与开关。  
2. **能静态则静态**：region/borrow/类型能证的，不重复收运行时税。  
3. **单权威**：语法只认 `docs/` + 编译器；Skills/MCP **只引用不改写**。  
4. **简单优先**：v1 合约表达式子集宁小勿大；复杂证明器不进默认产品。  
5. **AI 可解析**：诊断、合约失败消息、doc 必须稳定字段/错误码。  
6. **性能默认正确**：release 默认无检查税；enforce 显式。  
7. **平台标注**：SHARED 语义双端验（G.8）。  
8. **一条债一层**：合约 parser、插桩 codegen、std 示范分 commit。

## 8. 非目标（写清避免膨胀）

| 非目标 | 原因 |
|--------|------|
| 自举期内完整 DbC + 证明器 | 与 residual 爆炸半径重叠 |
| 兼容 Eiffel/C++26 全语义 | 学习成本与实现量爆炸 |
| 用合约替代 unsafe 审计 | 威胁模型不同 |
| Agent 自动 `git push` / 改系统 | 安全 |
| 在 MCP 内再实现一套 typeck | 双权威 |
| 要求所有私有函数写满 ensures | 噪声；先抓 `export` / 安全边界 API |
